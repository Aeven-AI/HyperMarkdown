# Streaming benchmark

A head-to-head of five React markdown renderers doing the thing that matters
while a model is talking: taking one more chunk and getting it on screen.

```bash
npm install
npm run bench                          # the default sweep
node run.js --runs=5 --warmup=1              # publication-quality sweep
node run.js --chunk=24 --runs=3 --warmup=1   # override every chunk size
node run.js --only=HyperMarkdown,Streamdown  # a subset
node run.js --fixture=table                  # one fixture
```

Results land in `results/latest.md` and `results/latest.json`.
The Markdown report records the median and measured range; the JSON retains
every raw measured sample plus the runtime and machine environment.

## What is measured

For each renderer × fixture, the document is split into fixed-size chunks and
fed in one at a time. Each frame is timed around **both** the write and the
render:

```js
const t0 = performance.now();
stream.write(chunk);
flushSync(() => root.render(stream.element()));
frames.push(performance.now() - t0);
```

Both halves have to be inside the window. For renderers that accumulate a
string and parse in the component, the work is in `render`; for HyperMarkdown,
`write()` *is* the parse. Timing only one of them flatters one design.

`flushSync` rather than `act()`: `act` only exists in React's development
build, and development React is several times slower than the one you ship.
Both force the commit to finish before returning. Between frames the event
loop is allowed one turn, so effects, timers and rAF callbacks run as they
would in a browser — some renderers schedule their next step from one.

Each measurement runs in **its own process** under `NODE_ENV=production`. A
shared process lets jsdom garbage and React fibers from earlier runs distort
later ones, and over thousands of frames it exhausts the heap outright.

With multiple measured runs, the report uses the run with the median total
time. The JSON also retains every measured sample so variance and alternative
aggregations can be checked without rerunning the benchmark.

## Reading the results

**Check the DOM-nodes column before the times.** The renderers do not all put
the same thing on screen for the same input, and the column is there to make
that visible. On `code-large`, markstream-react finishes with 54 nodes where
HyperMarkdown has 1,354 — it is deferring the block, not rendering it faster.
react-markdown's 4 nodes are legitimate: a code block really is one `<pre>`,
one `<code>` and one text node, however long the code is.

The absolute numbers are from one machine on one day. The ratios travel; the
milliseconds do not. Regenerate rather than quoting these.

## The renderers

| renderer | strategy |
| --- | --- |
| HyperMarkdown | sub-block cache — per code line, table row and list item |
| Streamdown | block-level memoization of top-level blocks |
| markstream-react | its own streaming parser, one component per node, memoized on node identity |
| deepseek-harness | freeze every block but the trailing two |
| react-markdown | none; the whole document is reparsed every chunk |
| markdown-it | baseline only — parse to an HTML string, `innerHTML`, no components |

`markdown-it` is a **floor, not an alternative**. It parses to an HTML string
and hands it to the DOM, so every frame replaces the whole subtree: nothing
keeps identity, state or an event handler, there are no copy buttons or
diagram components, and it does no sanitisation. It is in the table to answer
"how much of this cost is markdown parsing, and how much is being a component
tree?" — the answer turns out to be that parsing is not the expensive part.

`deepseek-harness` is not their shipped renderer. `vendor/deepseek-incremental.js`
is their `incremental.ts` copied verbatim, paired with a plain unified
pipeline, because their renderer depends on components and CSS modules from
inside their repo. It measures how much work their freeze-the-prefix strategy
leaves per chunk, which is the comparable part — read it as an upper bound on
that strategy's cost, not as their product. See `vendor/README.md`.

## The fixtures

Generated by `node fixtures/build.js`, deterministic so runs compare.

| fixture | shape | what it stresses |
| --- | --- | --- |
| `code-large.md` | one 57 KB fenced block | a single block that never stops growing — block-level freezing cannot help |
| `table-large.md` | 400-row GFM table | same, plus inline markup in every cell |
| `prose-mixed.md` | 60 sections of headings, prose, lists, quotes | many small blocks, where block-level freezing does help |

Two further fixtures are captured from real model output rather than generated
— `real-code-os.md` (34 KB, one 33 KB fenced block) and `real-table-head.md`
(10 KB, one 10 KB table). Run those with `--chunk=8`, which is the chunk size
the captured streams actually arrived in; the synthetic fixtures default to 64
and understate how many frames a real stream produces.

## Known harness quirks

`prepare.js` copies the built package in rather than linking it, and rewrites
its `tippy.js` import to `vendor/tippy-interop.js`. Both are Node-ESM
artefacts that a bundler handles and that would otherwise stop the benchmark
running at all — see the comments in those files. Neither changes what is
measured.
